Redis Data Integration in one slide

RDI keeps Redis Enterprise continuously in sync with your primary database using Change Data Capture — no app code required.

Oracle / Postgres system of record
→
RDI CDC + transform
→
Redis Enterprise hot cache, sub-ms reads

Capture

Debezium-based CDC. Reads the database's own redo log — zero load on your application tables.

Transform

YAML jobs. Pick columns, filter rows, set the key pattern, pick the target structure (JSON / Hash / Stream / Sorted Set).

Deliver

Writes into Redis Enterprise with at-least-once guarantee. ~10k records/sec per core, auto back-pressure, full observability.

All driven by a small YAML file, no Java, no Python, no Kafka."

How RDI is deployed

Three planes — standard RDI deployment topology:

  • Data plane: Debezium collector + stream processor. Two VMs, active/standby with leader election.
  • Control plane: operator + REST API + Prometheus exporter, running on the same VMs.
  • Management plane: redis-di CLI + Redis Insight pipeline editor.

RDI's own state — CDC streams, checkpoints, schema history — sits inside Redis Enterprise. Nothing is persisted on the RDI VMs. That keeps your security and operational posture simple.

For the firm deployment

  • 2 RDI VMs (or 2 K8s pods) per environment
  • RDI's "state DB" on your existing Redis Enterprise cluster — 250 MB shard pair
  • Source: 1 read connection into Oracle, using the existing CDC user we already configure for GoldenGate / Streams
  • Target: any number of Redis Enterprise DBs — same cluster or different ones per workload

All the state RDI needs lives in Redis Enterprise on your existing cluster — there is nothing else for you to back up. That matters for your operations team and your auditors."

Pipeline lifecycle — what happens when you click "Deploy"

  1. Validate — RDI checks your config.yaml and job files for syntax, connectivity to source & target, and that the publication / log positions exist.
  2. Snapshot — the collector reads the full set of selected rows in parallel workers and writes them through the transformations into Redis Enterprise. This is your day-1 prefetch — no cold cache.
  3. CDC — once snapshot completes, RDI flips to streaming mode and tails the Oracle redo / Postgres WAL. New trades, price ticks, holding updates flow to Redis in hundreds of milliseconds.
  4. Update — need to add a column, a new table, a new transformation? Edit YAML, deploy. RDI applies the change without resetting the pipeline.
  5. Reset (rare) — want to rebuild a target DB from scratch? One CLI command and you are back to step 2.
Talk track
"This is the lifecycle. The key word here is snapshot — on day 1, RDI prefetches your whole dataset. So the very first user request after go-live is already hot. That's the difference between cache-aside and cache-prefetching. You stop paying the cold start tax."

A complete RDI job — 10 lines

source:
  server_name: sectrade
  schema: portfolio
  table: holding
output:
  - uses: redis.write
    with:
      connection: target
      data_type: json
      key:
        expression: concat(['holding:', to_string(customer_id), ':', to_string(security_id)])
        language: jmespath

That's it. That single file keeps the Redis holding:{cust}:{sec} JSON document in sync forever with the portfolio.holding table.

Security & compliance answers up-front

  • Data in transit: TLS / mTLS on every hop — source ↔ RDI ↔ target.
  • Data at rest: RDI never persists data to disk on the VMs. All state goes through Redis Enterprise, which inherits your cluster's encryption-at-rest setting.
  • Credentials: stored as RDI secrets (file system or K8s secrets), referenced by name in config.yaml. Never in plaintext.
  • RBAC: source DB user can be replication-only; target DB ACL can be write-only for the RDI processor and read-only for your applications.
  • Audit: structured JSON logs per-pipeline, integrate with Splunk, ELK, Datadog — whatever you already have.
  • Air-gapped option: RDI runs on your VMs / K8s — no outbound calls to Redis cloud needed. Ships as offline-installable.
